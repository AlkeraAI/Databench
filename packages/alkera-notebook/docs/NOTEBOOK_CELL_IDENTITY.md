# Notebook cell identity

This document is normative for format 1.0 of the notebook file format (`NOTEBOOK_FORMAT_SPEC.md`). It defines how a cell id is stored, encoded and recovered. Section 3 records the alternatives that were measured and why they were not used.

## 1. Requirements

A cell id names one cell of one notebook for as long as that cell exists. Comments, saved outputs, run records, app tiles and agent references point at it.

| # | Requirement |
| --- | --- |
| I1 | Stable across edits to the cell's code, renames, reorders and moves within the notebook |
| I2 | Survives copy and paste between notebooks without colliding with the target's ids |
| I3 | Git merges of concurrent inserts, deletes and reorders merge without conflicts that involve ids |
| I4 | Survives a save by stock marimo as well as the format allows, and never reassigns an id to the wrong cell when it cannot |
| I5 | No false reassignment anywhere: when the reader is unsure, it mints a new id |
| I6 | Deterministic: the same file and the same known prior state always resolve to the same ids, on every machine |
| I7 | Minimal diff noise: an edit to one cell changes no line outside that cell |
| I8 | Implementable by others from this document alone, with no server |
| I9 | Invisible in the cell's code; the file stays a valid marimo notebook that stock marimo opens and runs |

## 2. Prior art

- **Jupyter (nbformat 4.5, JEP 62).** Each cell carries an `id` field (`^[a-zA-Z0-9-_]{1,64}$`, unique per notebook). The id lives inside the cell's own JSON object, so it moves with the cell through reorders and merges. JupyterLab gives pasted cells new ids; nbformat's validator can repair duplicate ids.
- **Pluto.jl.** A UUID comment line before each cell (`# ╔═╡ <uuid>`) plus a `# ╔═╡ Cell order:` footer that lists every UUID. Pluto owns its parser, so the comments are safe for it. The order footer is a second, positional copy of the ids, and concurrent inserts edit it on both branches.
- **Hex (`.hex.yaml`), Deepnote (`.deepnote`).** A UUID field on each cell object in YAML.
- **marimo.** No id in the file. Ids are regenerated by position on every load (`CellIdGenerator(seed=42)`). On file reload it re-matches old ids to new cells with `match_cell_ids_by_similarity`, a prefix and suffix score solved by assignment, with no rejection threshold.

The pattern every format that keeps ids shares is the same: **the id is stored with the cell it names**, and nothing else in the file repeats it.

## 3. Options evaluated

Measured with marimo 0.25.1, by writing each candidate into a notebook, running it, checking it and saving it through marimo. "Survives" means the id is still in the file after marimo's own editor save path (`load_app` then `generate_filecontents`).

| Option | Runs | `marimo check` / `--strict` | Survives stock save | Verdict |
| --- | --- | --- | --- | --- |
| A. Decorator keyword `@app.cell(alkera_id="...")` | yes | 0 / **1** (one warning per cell) | **no** | **chosen as the carrier** |
| B. Function name `def _k2m9q7xh3c():` | yes | 0 / 0 | **yes** | rejected (below) |
| C. Header map of ids with code fingerprints, sorted by id | yes | 0 / 0 | yes (verbatim, then stale) | rejected (below) |
| D. Sidecar file beside the notebook | n/a | n/a | yes | rejected (below) |
| E. marimo upstream cell-id support | n/a | n/a | n/a | not available; option A's keyword is offered upstream |
| F. Content-addressed ids (hash of the code) | yes | 0 / 0 | n/a | rejected: changes on every edit (fails I1) |
| G. Comment as the first body line | yes | 0 / 0 | yes | rejected: visible and editable in every editor, copied with the code (fails I9) |
| H. Comment on, above, or below the decorator | yes, except below (breaks the cell) | | **no** | rejected: no better than A, and "below" corrupts the file |

Why not B (function name), even though it is the only carrier that survives a stock save with no warning:
- The function name **is** marimo's user-facing cell name: shown in its editor, used to call cells from tests (`test_*` cells run under pytest) and to refer to cells. Spending it on an id takes that feature away, or forces names like `load_data__k2m9q7xh3c` that people see and that a stock-marimo rename destroys.
- It cannot work for `@app.function` and `@app.class_definition` cells (their name is the Python function or class) or the setup cell (no name).

Why not C (header map with fingerprints, sorted by id):
- A fingerprint must change when the code changes, so every cell edit also edits a header line far from the cell (fails I7). Without fingerprints, the map is only a positional list, and positional fallback after a stock-marimo reorder or an insert-plus-delete assigns ids to the wrong cells (fails I5).
- Sorting by id reduces but does not remove merge conflicts, and it is a second copy of information the cells already hold.

Why not D (sidecar): it is separated from the notebook by every copy, upload and partial commit, and it is a second file to merge.

## 4. The rule

**Each cell carries its id as the first keyword of its own marimo decorator, and nothing else in the file repeats it.** When a tool has stripped the keywords (a stock marimo save), ids are recovered by matching against the last state the reader knows, with a similarity threshold, and minted deterministically when no match is good enough.

This meets I1 to I3 and I6 to I9 fully. It meets I4 to the extent the format allows without fighting marimo: a stock save loses the keywords, and the reader recovers them from the previous version whenever one is available (the live document, or a file given with `--known`), and never guesses. I5 holds unconditionally.

The marimo build vendored in this repository keeps `alkera_*` keywords through its parse and save without a warning (`PASSTHROUGH_PREFIXES` in `vendor/marimo/marimo/_ast/cell.py`). The same pass-through is offered upstream; if marimo adopts it, stock saves keep ids too, with no format change.

## 5. Encoding

- Ten characters from the lower-case Crockford base32 alphabet `0123456789abcdefghjkmnpqrstvwxyz`, regular expression `^[0-9a-hjkmnp-tv-z]{10}$` (50 bits). This satisfies nbformat's id pattern, so `.ipynb` export uses the id unchanged.
- Ids are unique within one notebook and mean nothing outside it. A reference across notebooks is the pair (notebook file id, cell id).
- New cells created by an editor get 50 random bits (`secrets`). Ids minted by the reader are deterministic (section 6.4).
- A cell id that comes back through history (a git revert, an undo) is the same cell coming back; that is intended.

## 6. Carrier and resolution

### 6.1 Carrier (writer rules)

- Every cell form carries `alkera_id="<id>"` as its **first** keyword, written as a Python string literal: `@app.cell(alkera_id="...")`, `@app.function(alkera_id="...")`, `@app.class_definition(alkera_id="...")`, `with app.setup(alkera_id="..."):`, and as a keyword of `app._unparsable_cell(...)` after `name=`.
- A writer writes an id on every cell, every time. A file a conforming writer produced therefore always has a complete set of keyword ids.

### 6.2 Inputs to resolution

- The cells of the file in file order, each with its parsed `alkera_id` keyword (or none) and its **normalized code**: the cell's code as marimo's parser returns it, with trailing whitespace removed from each line and trailing blank lines removed.
- Optionally, a **known state** `K`: an ordered map `id -> normalized code` describing the last version of this notebook the reader trusts. The server passes the live document's cells, and `alkera-notebook run --known <file>` passes the cells of the file given. Without either, `K` is empty.

### 6.3 Algorithm

```
resolve(cells, K):
  taken = {}                                            # id -> cell index
  # 1. keywords
  for i, cell in cells (file order):
      k = cell.keyword
      if k is None or not ID_RE.fullmatch(k): continue          # invalid keywords are ignored (violation recorded)
      if k not in taken: taken[k] = i; continue
      # duplicate keyword: keep it on the cell whose code equals K[k] exactly,
      # else on the earlier cell; the other cell becomes unresolved
      j = taken[k]
      if k in K and cell.code == K[k] and cells[j].code != K[k]: taken[k] = i; unresolve(j)
      else: unresolve(i)
  U = cells without an id, in file order
  A = [id for id in K if id not in taken]                       # in K's order
  # 2. exact code match
  for each u in U:
      matches = [a in A with K[a] == u.code]
      if matches: assign(u, matches[0]); remove it from A
  # 3. similarity match with a threshold
  pairs = [(ratio(u.code, K[a]), u.index, a) for u in U for a in A if ratio >= 0.6]
  sort pairs by (-ratio, u.index, a)
  for (r, ui, a) in pairs: if neither ui nor a assigned yet: assign
  # 4. deterministic minting
  for each u still in U (file order): assign(u, mint(u.code, used ids))
```

- `ratio(x, y)` is `difflib.SequenceMatcher(None, x, y, autojunk=False).ratio()` over the normalized code strings, computed only when `SequenceMatcher.real_quick_ratio()` and `quick_ratio()` are both at least 0.6 (same result, cheaper). Both strings are truncated to their first 65,536 characters.
- `mint(code, used)`: for `n = 0, 1, 2, ...`, take `sha256(b"alkera-cell-id\x00" + code.encode() + b"\x00" + str(n).encode())`, encode the first 50 bits in the alphabet above, and return the first result not in `used`. Two identical unresolved cells therefore get different, still deterministic, ids.
- Every resolved cell reports how: `keyword`, `exact`, `similar` (with the ratio), or `minted`. Ids of `K` that were not assigned are cells that no longer exist.

### 6.4 Properties and failure modes

| Situation | Result |
| --- | --- |
| Any edit, rename, reorder, move inside the notebook, git merge of concurrent changes | keyword resolution; no change |
| A cell copied within the notebook by text (duplicate keyword) | the copy whose code still equals the known state keeps the id; the other gets a new id |
| A cell pasted from another notebook by text | keeps its id unless it collides, then the duplicate rule applies; the web editor always gives pasted cells new ids |
| Stock marimo saved the file (keywords gone), known state available | unchanged cells: `exact`; edited cells: `similar` when at least 60% alike; inserted cells: `minted`; deleted cells: their ids are released |
| The same, a cell edited beyond recognition | treated as deleted plus inserted: a new id. Attachments (comments, saved outputs) are not moved onto unrelated code |
| Stock marimo saved the file, no known state | every cell `minted`. Continuity is lost and nothing is misattributed |
| Keywords present but malformed | ignored for that cell, which resolves through steps 2 to 4; a violation is reported |
| marimo's own matcher, for comparison | deleting `df = pl.read_csv(...)` and adding an unrelated `url = ...` cell gives the new cell the deleted cell's id; the threshold above prevents exactly this |

## 7. Tests (part of the format corpus)

- Corpus cases: every cell form with a keyword; keywords stripped with a known state after (a) no structural change, (b) a reorder, (c) an insert plus a delete at equal count, (d) a delete of one cell and an insert of an unrelated one (must mint), (e) an edit of 30% of a cell (must match), (f) an edit beyond the threshold (must mint); duplicate keywords with and without a known state; two identical cells without keywords (two distinct minted ids, stable across runs); malformed keywords.
- A property test (Hypothesis): for random notebooks and random sequences of edits, renames, reorders, inserts and deletes, with keywords present, resolution returns exactly the original ids; with keywords stripped and a known state, no cell receives an id whose known code has a ratio below 0.6 with its own code.
- Determinism: resolving the same file and known state in two processes yields the same ids.

## 8. Known limitations

- Stock marimo logs one warning per cell for the unknown keyword, and `marimo check --strict` exits 1 on canonical files, until marimo accepts a keyword pass-through. Projects that gate CI on `marimo check --strict` must exclude `*.alknb.py` or run `alkera-notebook check` instead.
- A stock marimo save drops the keywords; continuity then depends on a known prior version being available.
